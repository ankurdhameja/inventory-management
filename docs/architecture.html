Architecture Overview

Factory Inventory Management System

A full-stack demo application for inventory tracking, order management, demand forecasting, and spending analytics across factory warehouses. Vue 3 frontend, FastAPI backend, in-memory JSON data — no database.

Tech Stack

Frontend

Vue 3 + Vite

  • Composition API
  • vue-router (6 top-level views)
  • axios for HTTP
  • Custom SVG charts, scoped CSS
localhost:3000
Backend

Python + FastAPI

  • Pydantic models for validation
  • Uvicorn ASGI server
  • Managed with uv
  • CORS open (demo only)
localhost:8001 (docs at /docs)
Data

In-memory JSON

  • Flat files in server/data/*.json

  • No database layer

System Architecture

Request / Data Flow

1

User changes a filter

Time period, warehouse, category, or order status changes in the UI. Filter state is held as module-level singleton refs in useFilters.js, shared across every view that imports it.

2

View requests data

getCurrentFilters() converts filter state into query params, and the view calls a method on client/src/api.js, which issues an axios GET to the FastAPI server.

3

FastAPI filters in memory

server/main.py applies apply_filters() (warehouse/category/status) and filter_by_month() (month or quarter) over lists already loaded into memory by mock_data.py.

4

Response validated & returned

Results are serialized through Pydantic response models (e.g. InventoryItem, Order) and returned as JSON.

5

Vue re-renders

Raw API data lands in refs (e.g. allOrders, inventoryItems); everything derived — totals, chart series, tables — is a computed() that recalculates automatically.

Notes on the Architecture

Filter state is a singleton, not per-component. All views share one filter set via module-level refs in useFilters.js — changing a filter on one view affects every other view using it.
Auth and i18n are client-only mocks. useAuth.js hardcodes a logged-in user; useI18n.js + locales/{en,ja}.js swap display strings. Neither touches the backend.
Gap: api.js defines getTasks/createTask/createPurchaseOrder methods with no matching /api/tasks or /api/purchase-orders routes in main.py. Tasks actually come from mock user data in useAuth.js; purchase orders are only read via the has_purchase_order flag on /api/backlog.
Demo application only: no database, no authentication, CORS open to all origins — not production-ready as-is.
